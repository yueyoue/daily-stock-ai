# 财务数据管线与增量采集（v1）

> 适用版本：`feat/bw-value-model`（估值模型 bw-value-v1.0 之后）。
> 配套文档：`docs/估值模型-bw-value-v1.md`（模型本身的规则与接口）。
> 本文面向"要继续改这里的人"：看完能知道数据从哪来、存在哪、为什么这么设计、哪里会踩坑、想加功能该动哪。

## 一、这次解决的是什么问题

估值模型上线后暴露一个硬事实：`stock_finance` / `stock_fin_indicator` 两张表原本是空的，模型只能靠东财快照兜底算 PE/PB，`pass` 永远是 0。补齐财务数据时遇到三个问题，本版一次性解决：

| 问题 | 现象 | 本版做法 |
|---|---|---|
| 库会无限膨胀 | 东财三表接口一次返回**全部历史**（000001 实测 123 期 ≈ 30 年、594.7 KB/票）→ 全市场约 4 GB | 采集时只入库最近 **40 期（≈10 年）**，超出部分在写库前丢弃；入库后再按票剪枝兜底 |
| 每季度重采很慢 | `sync_finance_for_code` 每次都全量拉全历史 → 5580 只重跑 15~30 小时 | 新增**公告驱动增量**：按公告日期查出新披露的票，只采那几只（实测 2026Q3 全市场 5813 家 → 近 3 天只 4 家，几秒） |
| 回测有前视偏差 | 两张财务表只有 `report_date`，4 月底披露的年报被当成 1 月已知 | 新增 `announce_date`（公告日期）并按东财业绩报表回填，供回测做 as-of 取数 |

## 三、三个设计决策（改之前先读这部分）

### 1. 为什么是 40 期，不是"日期减 10 年"

40 个报告期 = 10 个自然年（40 = 10×4）。按"日期减 10 年"切会在边界上错删：财报披露有滞后，2026-11 跑采集时 `today-10y = 2016-11`，而 2016 年报是 2017 年才披露的，按日期切会把它误删。按"最近 40 期"切天然跟随披露节奏，边界永远落在季度末。

窗口参数集中在两个地方，改时两处一起改：
- `backend/app/services/finance.py`：`DEFAULT_MAX_PERIODS = 40`
- `backend/scripts/backfill_finance.py` / `incremental_finance.py`：`--max-periods` 默认 40

### 2. 为什么"全量拉下来再截断"，而不是让接口只给 10 年

东财三表接口（`stock_{balance,profit,cash_flow}_sheet_by_report_em`）**没有时间范围参数**，一次返回整段历史。所以只能在客户端截断：`sync_finance_limited` 先按 `report_date` 倒序排，取前 N 期再 `upsert`。

代价：首次全链路下载量不变（15~30 小时是下载决定的，省不了），但库体积可控（4 GB → 约 1.5 GB）。

### 3. 为什么增量用"公告清单差分"，不是"订阅推送"

东财没有变更流接口，但**支持按公告日期过滤**，这是关键发现（实测）：

```
报告期 2026-09-30 全市场           → 5813 家
加 (NOTICE_DATE>='2026-11-18')     → 7 家（1 页）
加 (NOTICE_DATE>='2026-11-19')     → 4 家
```

所以增量 = 拉"N 天内公告"的清单 → 得到股票代码 → 对这些代码跑单票采集。每次 1~3 个请求，秒级。

重复采集是幂等的（`upsert` 按 `(code, report_date)`），因此**默认每次回看 3 天**——宁可重采，不漏采。

## 四、数据流

```
① 清单层（每次增量）
   GET datacenter-web.eastmoney.com/api/data/v1/get
       reportName=RPT_LICO_FN_CPD          （业绩报表，正式财报）
       filter=(REPORTDATE='2026-09-30')(NOTICE_DATE>='2026-11-19')
   GET datacenter.eastmoney.com/securities/api/data/v1/get
       reportName=RPT_PUBLIC_OP_NEWPREDICT （业绩预告，仅提示，不入库）
       注意：预告接口域名是 datacenter.eastmoney.com，不是 datacenter-web

② 采集层（按股票逐只）
   collect_with_fallback → akshare 东财三表（主）→ 新浪三表（备）
   ↓
   sync_finance_limited(code, max_periods=40)
       → 按 report_date 倒序截断 → upsert_finance（(code, report_date) 主键，空值不覆盖）

③ 收口层（同一只票，采成功后立即）
   prune_finance(code, 40)        删除超出 40 期的报表行 + 指标行（默认不归档）
   set_announce_dates(code)       拉 RPT_LICO_FN_CPD by SECURITY_CODE，回填 report_date → announce_date
   sync_fin_indicators(code)      按窗口内报表重算 30 项指标

④ 状态层
   data/finance_progress.json        全量回填进度（页面 8 秒轮询）
   data/finance_incremental.json     增量结果（latest run）
   frontend/dist/assets/*.json       上面两份的副本，给静态页直接读
```

**顺序很重要**：先剪枝、后算指标。反过来会先按 123 期算一遍指标、再删掉 83 期，白跑。

## 五、数据库变更

```sql
ALTER TABLE stock_finance ADD COLUMN announce_date DATE NULL AFTER report_type;
```

- 已有迁移：`0004_finance_announce_date`（带存在性护栏，新库由 0001 `create_all` 建出）。
- `stock_fin_indicator` **不加**公告日：指标是按报告期算的派生数据，回测 join `stock_finance` 取公告日即可，避免两份口径不同步。
- 权限/口径提醒：`announce_date` 允许 NULL。NULL 只代表"还没回填"，**不要**在回测里把 NULL 当 `report_date` 用，这会重新引入前视偏差；缺失时应把该期视为"该时点不可用"。

## 六、接口

| 方法 | 路径 | 参数 | 说明 |
|---|---|---|---|
| POST | `/api/model/collect/start` | `limit`、`workers`(≤12)、`reset` | 启动全量回填（后台，可断点续跑） |
| GET | `/api/model/collect/status` | — | 回填进度 + 进程存活 |
| POST | `/api/model/collect/incremental` | `days`(1~30，默认 3)、`workers`(≤8)、`dry_run` | 启动增量采集；全量在跑时拒绝启动 |
| GET | `/api/model/collect/incremental/status` | — | 增量状态 + 进程存活 |

**进程存活判断**（两个接口都用）：读 pid 文件 → `os.kill(pid,0)` → 再读 `/proc/{pid}/cmdline` 确认命令行含脚本名。只看 pid 会因 pid 复用误判"还在跑"（v3 踩过）。

状态 JSON 关键字段：`total/done/failed/percent/rate_per_min/eta_min/last_code/last_status/max_periods/pruned_finance/pruned_indicator`；增量另有 `discovered/collected/unsupported/pruned/since/quarters`。

## 七、运维手册

```bash
# 容器内执行需要 PYTHONPATH=/app（脚本 import app.*）
source /dev/stdin <<'EOS'
docker exec -e PYTHONPATH=/app dsa-app python /app/data/backfill_finance.py --workers 4
EOS

# 1) 首次全量回填（约 9~12 小时 @ workers=4）
docker exec -e PYTHONPATH=/app dsa-app python /app/data/backfill_finance.py --workers 4

# 2) 先小批量验证（强烈建议首次这么做）
docker exec -e PYTHONPATH=/app dsa-app python /app/data/backfill_finance.py --limit 5 --workers 2

# 3) 只剪枝、不联网（先 dry-run 报数，确认后再真删）
docker exec -e PYTHONPATH=/app dsa-app python /app/data/backfill_finance.py --prune-only --dry-run
docker exec -e PYTHONPATH=/app dsa-app python /app/data/backfill_finance.py --prune-only

# 4) 日常增量：只采最近有新公告的票
docker exec -e PYTHONPATH=/app dsa-app python /app/data/incremental_finance.py --days 3 --workers 3

# 5) 只看看今天谁会采（不入库）
docker exec -e PYTHONPATH=/app dsa-app python /app/data/incremental_finance.py --days 3 --dry-run

# 6) 定向补某只票
docker exec -e PYTHONPATH=/app dsa-app python /app/data/incremental_finance.py --codes 600519

# 7) 想保留被删数据时（默认不归档！见"踩坑 6"）
docker exec -e PYTHONPATH=/app dsa-app python /app/data/incremental_finance.py --days 3 --archive-dir /app/data/prune_archive
```

**回填中断后**：直接重跑同一命令即可，`data/finance_done.txt` 是追加式断点。

**验证是否生效**：
```sql
-- 每票期数应 ≤ 40，且起点约 10 年前
SELECT code, COUNT(*), MIN(report_date), MAX(report_date),
       SUM(announce_date IS NOT NULL) AS ann
FROM stock_finance GROUP BY code ORDER BY code LIMIT 10;
```

## 八、部署方式（飞牛 / Docker）

项目是**源码挂载**部署，不需要重建镜像：

```yaml
# docker-compose.override.yml
volumes:
  - ./src/backend/app:/app/app                 # 后端源码
  - ./src/frontend/dist:/app/frontend/dist      # 前端产物
# docker-compose.yml
volumes:
  - /vol1/docker/daily-stock-ai/data:/app/data  # 脚本 + 状态 + 归档
```

步骤：
1. 改 `src/backend/app/**` 的文件会立即生效于容器内 `/app/app`，但需 `docker restart dsa-app` 让 uvicorn 重新导入；
2. 数据脚本放宿主 `/vol1/docker/daily-stock-ai/data/`（对应 `/app/data`），改完**不需要**重启容器；
3. 静态页放 `src/frontend/dist/assets/model.html`，改完直接刷新浏览器（注意：`dist/model.html` 会被 SPA 回退成 `index.html`，**必须放 `assets/`**）。

## 九、踩坑记录（都是实际调试出来的，别再踩）

1. **东财三表必须带交易所前缀**：`SH600519` 能取到，`000001` 取不到。`collectors/finance.py::_em_symbol` 负责补 `SH/SZ/BJ`。
2. **利润表/现金流量表要按 ctype 试**：akshare 内部按 `hidctype` 取数，不同板块对应 ctype 1~4 不同，需 `4→3→2→1` 逐个试（`_install_ctype_patch`）。
3. **指标表不会自动生成**：`sync_finance_for_code` 只写报表，指标要靠 `sync_fin_indicators` 另跑；早期"报表有数、模型读不到"就是漏了这步。
4. **子进程必须带 `PYTHONPATH=/app`**：脚本 `import app.*` 需要它，否则 `ModuleNotFoundError: No module named 'app'`。
5. **pid 文件不能只看活**：崩溃后 pid 会被复用，`os.kill(pid,0)` 会误判"还在跑"。要读 `/proc/{pid}/cmdline` 校验脚本名。
6. **剪枝归档会吃掉省下的空间**：单票归档 0.3~0.6 MB（000001 353 KB / 000002 628 KB），5580 只就是 **1.5~3 GB**，几乎抵消 4 GB → 1.5 GB 的收益。因此 `--archive-dir` **默认空（不归档）**，只在排查问题或小批量时显式开启。
7. **北交所（4/8/92 开头）三表无数据**：实测 `BJ832532` 东财 F10 返回空、`SH600519` 正常 104 期。这不是代码 bug，是数据源不覆盖。脚本对这类票标 `unsupported` 并跳过，**不计 failed**，否则进度条永远收不了尾、还会无限重试。
8. **预告 ≠ 报表**：`RPT_PUBLIC_OP_NEWPREDICT`（业绩预告）只给区间值（"预增 50%~70%"），没有三表科目。它只能当"这家要出数了"的提示，真正入库必须等 `RPT_LICO_FN_CPD`（业绩报表）。
9. **东财快照接口会限流**：`push2.eastmoney.com` 在容器内出现过 `RemoteDisconnected`。`valuation.py` 已有缓存 + 退避（TTL 60 分钟、失败退避 10 分钟、失败回退旧缓存），改这块时别把退避去掉。

## 十、已知限制（别当成 bug）

| 限制 | 影响 | 现状 |
|---|---|---|
| 北交所无三表 | 约 260 只票只有 K 线与快照，PCF、财报可信度 gate 会 `skipped` | 已标 `unsupported` |
| 首次全量需 9~12 小时（workers=4） | 期间 `scan` 仍是 `source=spot` | 断点续跑，可分批 |
| 公告日只能"逐步补齐" | 首次回填的 40 期若没跑过增量，`announce_date` 可能为 NULL | 增量每天跑会自动补近期；历史可用 `--codes` 定向补 |
| `announce_date` 无复权/更正跟踪 | 同一报告期如果更正公告，只保留最新公告日 | 需要更精细可加 `announce_date` 历史表 |
| 增量不覆盖北交所 | 北交所票增量时直接跳过 | 同上 |

## 十一、后续开发指引

**想改保留年限** → 改 `DEFAULT_MAX_PERIODS`（服务层）+ 两个脚本 `--max-periods` 默认值；改小后先 `--prune-only --dry-run` 看会删多少。

**想给模型加财务因子** → 在 `valuation.build_snapshot` 里从 `StockFinIndicator.metrics` 取（该列是 JSON，30 项指标全量），再在 `bw_model` 的 `RULES/WEIGHTS` 加门槛或权重；不要在选股 DSL 里加（DSL 是全局 AND、不支持行业分组）。

**想把回测做成真正的 point-in-time** → 用 `announce_date` 而不是 `report_date` 过滤：
```python
q.filter(StockFinance.announce_date != None, StockFinance.announce_date <= trade_date)
```
`announce_date` 为 NULL 的期应视为"当时不可用"，不要让它们漏进来。

**想加分红/股息率采集** → 现在 `div_yield` 依赖快照的 f9/f23 派生值，没有原始分红表。加采集时注意：分红要按"除权日"入库，否则同样有前视偏差。

**想把增量挂到定时任务** → 项目已有 APScheduler（`app/scheduler/registry.py`），可注册每日 19:00 跑 `incremental_finance.py`；财报季（1/4/7/8/10 月）可提高到每日 2 次。

**想改增量触发源** → 除了 `RPT_LICO_FN_CPD`，还可试 `RPT_PUBLIC_BS_APPOIN`（预约披露时间，实测 2026-12-31 当期返回空，需等交易所发布）——它能提前知道"哪天谁披露"，命中率更高。
